POSTGRESQL & DATABASE OPERATIONS · RELEASE 5.27.0

PostgreSQL Healthcare Warehouse Operations

Move the clinical warehouse into PostgreSQL with transactional ETL, idempotent upserts, patient history and database operations.

Warehouse enginePostgreSQL15+ recommended
ETL behaviorUPSERTTransactional resource loading
Patient historySCD Type 2Versioned patient attributes

Deployment workflow

Requires PostgreSQL
  1. Run the v5.25 FHIR ETL to generate the four source CSV files.
  2. Apply sql/migrations/001_schema.sql using psql.
  3. Install the optional psycopg 3 dependency.
  4. Set HDA_PG_DSN securely in your shell environment.
  5. Run the loader and inspect row counts and mart outputs.
psql "$HDA_PG_DSN" -v ON_ERROR_STOP=1 -f postgresql_healthcare_warehouse_operations_v527/sql/migrations/001_schema.sql
python -m pip install -r postgresql_healthcare_warehouse_operations_v527/requirements.txt
python postgresql_healthcare_warehouse_operations_v527/scripts/load_postgresql.py --source-dir healthcare_data_engineering_interoperability_v525/outputs/demo

Database engineering

  • PostgreSQL schema and relational constraints.
  • Parameterized psycopg 3 operations and transaction handling.
  • Idempotent upserts using stable resource identifiers.
  • Indexes for patient/date, terminology/date and encounter lookups.
  • Materialized encounter summary and patient cohort mart.

Historical patient tracking

Patient demographic changes are hashed and compared with the current dimension row. Changed attributes close the prior version and insert a new current version; unchanged reruns do not create new versions.

Test with multiple synthetic snapshots before using this pattern in a production warehouse.

Security and performance

  • Separate analyst and loader group roles.
  • Keep credentials in environment variables or a secret manager.
  • Use EXPLAIN (ANALYZE, BUFFERS) with representative data.
  • Measure index benefit; do not infer performance from tiny synthetic tables.

Execution status: SQL and helper tests are checked, but no live PostgreSQL server was available for end-to-end integration.

DATA WAREHOUSING & SQL ENGINEERING · RELEASE 5.26.0

Clinical Data Warehouse & Advanced SQL Engineering

Transform interoperable clinical resources into dimensional models, governed facts and analysis-ready data marts.

Warehouse dimensions4Date · Patient · Encounter · Terminology
Fact tables2Observation · MedicationRequest
Data marts2Encounter summary · Patient cohort

Build the warehouse

Local Python + SQLite

First run the v5.25 FHIR ETL pipeline, then execute:

python clinical_data_warehouse_sql_engineering_v526/scripts/build_warehouse.py --input-dir healthcare_data_engineering_interoperability_v525/outputs/demo --output-db clinical_data_warehouse_sql_engineering_v526/outputs/hospital_warehouse.sqlite --cohort-status finished

Creates dimensional tables, fact tables, analytical marts, integrity checks and a SHA-256 manifest.

Warehouse model

  • Dimensions: date, patient, encounter, terminology.
  • Facts: one row per Observation and MedicationRequest.
  • Marts: one row per Encounter and one row per qualifying Patient.
  • SQL: window functions, cohort summaries and trend analysis.

Data engineering principles

  • Declare table grain before designing joins.
  • Aggregate separate one-to-many facts before joining to avoid fanout.
  • Preserve analyte, unit, terminology and date keys.
  • Reconcile source counts, foreign keys and database integrity.

Slowly changing dimensions

Introduces Type 1 versus Type 2 dimension strategies. This release uses one synthetic patient snapshot and Type 1 loading; it does not claim a tested historical Type 2 pipeline.

SQL examples are in clinical_data_warehouse_sql_engineering_v526/sql/analytics_examples.sql.

CLINICAL RESEARCH METHODS · RELEASE 5.24.0

Clinical Research Methods & Advanced Modelling

Move beyond basic tests into effect sizes, paired and repeated-measures methods, internally validated prediction and study planning.

NonparametricCliff's δMann–Whitney + effect size CI
Repeated dataWilcoxon / FriedmanPaired and multi-condition methods
PredictionStratified CVROC AUC, Brier and calibration

Run the integrated clinical methods workflow

Local Python
python -m pip install -r clinical_research_methods_v524/requirements.txt
python clinical_research_methods_v524/scripts/clinical_methods.py --input clinical_research_methods_v524/data/synthetic_clinical_methods.csv --config clinical_research_methods_v524/templates/clinical_methods_config.json --output clinical_research_methods_v524/outputs/demo

Research methods

  • Mann–Whitney U with Cliff's delta and bootstrap confidence interval.
  • Paired Wilcoxon signed-rank with a separately labelled mean-change interval.
  • Friedman repeated-measures test and Kendall's W.
  • Power/sample-size planning for two independent means.
  • Descriptive missingness pattern assessment.

Predictive validation

  • Repeated stratified K-fold cross-validation.
  • Out-of-fold ROC AUC and Brier score.
  • Calibration intercept and slope.
  • Imputation and scaling fitted inside each training fold.

Interpretation safeguards

  • Mann–Whitney U and Cliff's delta are related but distinct summaries.
  • The paired Wilcoxon test and mean-change bootstrap interval target different estimands.
  • Friedman is complete-case; post-hoc contrasts are not automatic.
  • Cross-validation is internal validation, not external validation; nested CV is not included.
  • Descriptive missingness patterns cannot identify MCAR, MAR or MNAR.
  • Multiple imputation is not included. All included demo data are synthetic.

Diagnostics and methods

  • Group-level Shapiro–Wilk and median-centred Levene diagnostics.
  • Linear model: Breusch–Pagan, residual normality, HC3 robust standard errors, Cook's distance, leverage and VIF.
  • Seeded percentile bootstrap confidence intervals.
  • Holm family-wise error, Benjamini–Hochberg FDR and Bonferroni correction.

Outputs

  • validation_results.json — machine-readable results
  • validation_report.md — human-readable interpretation
  • validation_manifest.json — SHA-256 output provenance

Use v5.22 Integrated Reporting to assemble validated outputs with figures and publication tables.

Interpretation safeguards

  • Diagnostics inform statistical judgement; they do not prove that assumptions hold or automatically select a test.
  • HC3 robust standard errors do not fix confounding, dependence, nonlinearity or misspecification.
  • Bootstrap resampling assumes independent observations; clustered or paired designs need an appropriate resampling scheme.
  • Multiplicity correction applies only to the explicitly defined family of tests.
  • Logistic regression can fail or be unstable with sparse data or separation; Firth correction is not included.
  • The Academy view is instructional. Statistical execution occurs in local Python, not inside the browser.

Trusted local code

2. Load CSV and query

python scripts/execution_engine.py load-csv --project ./my_project --input data/raw/encounters.csv --table encounters

python scripts/execution_engine.py runs --project ./my_project

Run records and logs are stored within the project workspace. Browser UI documents commands; it does not execute Python or SQL.

Execution boundaries

  • Python scripts execute with your local user permissions; only run trusted code. This is not a sandbox.
  • SQLite SQL is read-only and capped at 100,000 rows.
  • CSV import stores source values as TEXT; explicit type conversion and validation remain part of analysis.
  • PostgreSQL, R, DAX and Power Query execution are not included in this release.
  • Logs are local records, not a tamper-proof audit trail.

Patient-data handling

Use synthetic or appropriately authorized data. Keep patient-level data, credentials and client-confidential material out of public Git repositories. Confirm institutional approval, access controls and retention requirements before processing real healthcare data.

INTERPRETATION RULES

What a result does—and does not—tell you

  • Relative effects need baseline risk context; a large relative reduction may correspond to a small absolute reduction.
  • NNT and NNH depend on outcome definition and follow-up duration. If the risk-difference interval crosses zero, a single NNT can conceal benefit and harm uncertainty.
  • Odds ratios are not risk ratios, particularly when outcomes are common.
  • PPV and NPV change with prevalence. Sensitivity and specificity may also vary across populations and thresholds.
  • Statistical significance is not clinical importance. Examine effect magnitude, precision, bias and applicability.
  • Do not treat an observational association as causal without a defensible causal design and assumptions.

INTERPRETATION CHECKLIST

Before reporting a result

  • State the estimand, population, outcome, contrast, time point and analysis population.
  • Report missingness and data exclusions; never silently code missing values as zero.
  • Inspect distributions, outliers, model residuals and influential observations.
  • Report effect estimates and confidence intervals alongside p-values.
  • Prespecify primary outcomes and address multiplicity; label exploratory work.
  • Separate statistical significance from clinical or operational importance.
  • Do not infer causality from an observational association.
